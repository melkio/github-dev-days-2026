# Design tecnico — Assegnazioni, scadenze e consultazione delle attività

Status: APPROVED

- Discovery sorgente: [docs/202610191514.discovery.md](202610191514.discovery.md)
- Piano di implementazione: [docs/202610191514.implementation-plan.md](202610191514.implementation-plan.md)

## 1. Problema e requisiti approvati

Estendere TaskFlow con: assegnatario facoltativo (un solo utente attivo), scadenza facoltativa come giorno di calendario `Europe/Rome`, filtri di consultazione (per assegnatario, non assegnate, scadute, per stato) e la nuova regola «Done è definitivo» (nessuna modifica, riapertura o eliminazione). Le regole di business e i criteri di accettazione 1–26 della discovery sono la fonte unica e non sono rimessi in discussione qui. La gestione utenti resta di sola lettura.

Nota: `SPECIFICATIONS.md` v1.0 dichiara assegnazioni e scadenze fuori scope e Done modificabile; la discovery li supera esplicitamente per questa evoluzione. README, `SPECIFICATIONS.md` (sezione fuori scope) e `docs/architecture.md` vanno aggiornati dove contraddetti.

## 2. Architettura attuale e vincoli di compatibilità

- Un solo progetto `TaskFlow.Api`, per feature: `Features/Tasks` (`TaskItem`, `TaskDtos`, `TaskEndpoints`, `TaskService`, `TaskStatus`), `Features/Users`, `Persistence` (`AppDbContext`, `DbSeeder`, `Migrations`).
- Gli endpoint fanno binding e validazione e producono `ValidationProblemDetails` (400) o `ProblemDetails` (404). `TaskService` contiene i workflow ed è l'unico accesso EF dei task. `PUT` aggiorna solo titolo e descrizione; `PATCH /status` solo lo stato; `204` per le modifiche.
- `TimeProvider` singleton; `ApiFactory` lo sostituisce con un clock fisso (2026-10-19 12:00Z) e usa SQLite in-memory aperto con migrazioni + seed.
- Elenco ordinato per `CreatedAtUtc` desc, poi `Id` asc (criterio di parità da riusare).
- Compatibilità: `PUT`, `PATCH /status`, `GET /api/tasks?status=` mantengono contratto e forma. Cambiano intenzionalmente solo i casi su task Done (ora `409`). `TaskDto` guadagna i campi `assigneeId` e `dueDate`.

## 4. Contratti API proposti

Convenzioni invariate: JSON camelCase, enum stringa, GUID formato `D`, liste vuote `200 []`.

### 4.1 Rappresentazione

`TaskDto` aggiunge `assigneeId` (`Guid?`) e `dueDate` (stringa `yyyy-MM-dd` o `null`):

```json
{ "id": "…", "title": "…", "description": null, "status": "Todo",
  "assigneeId": "10000000-0000-0000-0000-000000000001", "dueDate": "2026-10-25",
  "createdAtUtc": "…", "updatedAtUtc": "…" }
```

### 4.2 Endpoint

| Metodo | URL | Body | Successo | Errori |
|---|---|---|---|---|
| `POST` | `/api/tasks` | `title`, `description?`, `assigneeId?`, `dueDate?` | `201` + `Location` | `400` |
| `PUT` | `/api/tasks/{id}` | invariato (solo titolo/descrizione) | `204` | `400`, `404`, `409` se Done |
| `PATCH` | `/api/tasks/{id}/status` | invariato | `204` | `400`, `404`, `409` se Done |
| `PATCH` | `/api/tasks/{id}/assignee` | `{ "assigneeId": "guid" \| null }` | `204` | `400`, `404`, `409` se Done |
| `PATCH` | `/api/tasks/{id}/due-date` | `{ "dueDate": "yyyy-MM-dd" \| null }` | `204` | `400`, `404`, `409` se Done o scadenza passata |
| `DELETE` | `/api/tasks/{id}` | — | `204` | `400`, `404`, `409` se Done |
| `GET` | `/api/tasks` | query: `status`, `assigneeId`, `unassigned`, `overdue` | `200` | `400` |

`GET /api/tasks/{id}` invariato (con i nuovi campi).

### 4.3 Elenchi

- Filtri combinabili in AND: `status` (invariato, case-insensitive), `assigneeId` (GUID formato `D`), `unassigned=true`, `overdue=true`.
- `assigneeId` + `unassigned=true` → `400` (campo `unassigned`). `assigneeId` malformato o booleano non valido → `400`. `unassigned=false`/`overdue=false` equivalgono ad assenza del filtro.
- `assigneeId` di utente inesistente o inattivo → `200` con i task assegnati (eventualmente `[]`) (D4); non verifica l'esistenza.
- `overdue=true`: `Status != Done` e `DueDate < oggi(Europe/Rome)`; ordinamento `DueDate` asc, poi `CreatedAtUtc` desc, `Id` asc. Senza `overdue` l'ordine resta `CreatedAtUtc` desc, `Id` asc.
- Un utente senza attività, o nessun risultato → `200 []`.

### 4.4 Semantica di modifica

Ordine di valutazione (da confermare in approvazione):

1. `400` sintattico: GUID `id` malformato, body mancante, formato non valido (`dueDate` non `yyyy-MM-dd`, `assigneeId` non GUID).
2. `404` se il task non esiste.
3. `409` se Done (qualunque modifica, riapertura o delete, anche valore identico — D7), o se la scadenza esistente è `< oggi` e si tenta di sostituirla/rimuoverla con `PATCH due-date` (anche con valore identico).
4. `400` semantico: assegnatario inesistente o inattivo (campo `assigneeId`); nuova scadenza `< oggi` (campo `dueDate`).
5. Applicazione, aggiornamento `UpdatedAtUtc` da `TimeProvider`, `204`.

Regole aggiuntive:
- `PATCH assignee` su task Todo/InProgress è sempre consentito, anche con scadenza passata; `null` rimuove l'assegnazione; riassegnare lo stesso utente attivo è `204`.
- Body `{}` o senza proprietà equivale a `null` (D6): rimuove il valore.
- `PUT` e `PATCH status` verso lo stesso valore su task non Done restano `204` come oggi; Done→Done è `409`.
- Completare (`status=Done`) un task scaduto è consentito e mantiene la scadenza (AC 10); non serve assegnatario/scadenza (AC 13).
- `POST` con `assigneeId` inattivo/inesistente o `dueDate < oggi` → `400`; nessun task creato.

### 4.5 Esempi di errore

`409`:
```json
{ "title": "Conflict", "status": 409, "detail": "A completed task cannot be modified or deleted." }
```
`400`:
```json
{ "title": "One or more validation errors occurred.", "status": 400,
  "errors": { "assigneeId": ["Assignee must be an existing active user."] } }
```

## 5. Dominio e persistenza

- `TaskItem`: `Guid? AssigneeId`, `DateOnly? DueDate`. Nessuna navigation property (D9). `TaskDto`/request DTO separati; la richiesta usa `string?` per `assigneeId`/`dueDate` con parsing manuale (pattern dello stato) per produrre `ValidationProblemDetails`.
- `AppDbContext`: `DueDate` colonna `TEXT` `yyyy-MM-dd` (conversione esplicita se il mapping predefinito di EF 10 non coincide); `AssigneeId` FK verso `Users.Id`, `OnDelete(Restrict)`; indici su `AssigneeId` e `DueDate`.
- Migrazione SQLite aggiuntiva (nome es. `AddTaskAssigneeAndDueDate`): due colonne nullable, FK e indici; EF ricostruisce `Tasks` su SQLite. I dati esistenti, compresi i Done, restano con `NULL`. Il seed non assegna né pianifica nulla.
- Transazioni: ogni operazione è un singolo `SaveChangesAsync` (transazione implicita); nessuna transazione esplicita.
- Letture con `AsNoTracking()`, `CancellationToken` propagato, filtri e ordinamento tradotti in SQL.

## 6. Tempo, notifiche, idempotenza

- Nuovo componente interno (es. `ItalianCalendar` in `Features/Tasks`) con `Today()` = `DateOnly` di `TimeZoneInfo.ConvertTime(timeProvider.GetUtcNow(), Europe/Rome)`. Unico punto di calcolo; usato da validazione, immutabilità e filtro scadute. Le query passano `today` come parametro.
- Si assume `Europe/Rome` risolvibile su Linux/CI (tzdata); da verificare (R3).
- Scaduta ⇔ `Status != Done` ∧ `DueDate < today`; scadenza = oggi non è scaduta.
- Test con clock controllabile, inclusi giorno UTC ≠ giorno italiano e DST.
- Notifiche: non richieste, fuori scope. Idempotenza: `PATCH` è idempotente tranne dove D7 impone `409`.

## 7. Rischi e domande aperte

- **R1 (D6):** con assente = `null`, un body `{}` o con nome di proprietà errato rimuove assegnatario/scadenza. Per la scadenza è limitato dall'immutabilità dopo la data. Accettato dal Product Owner; da documentare in OpenAPI/README.
- **R2 (D8):** con check-then-save, una richiesta concorrente (es. `PUT` mentre il task diventa Done, o modifica della scadenza nel giorno in cui scade) può superare il blocco. Finestra ridotta ma non nulla; il requisito «definitivo» non è garantito sotto concorrenza. Accettato; mitigazione futura: token di concorrenza o update condizionali.
- **R3:** disponibilità dati tz `Europe/Rome` nell'ambiente di esecuzione; richiede un test dedicato.
- **R4:** la ricostruzione di `Tasks` nella migrazione SQLite va verificata su dati esistenti.
- **R5:** `409` è nuovo nel progetto; OpenAPI e README devono documentarlo.
- **R6:** nuova stringa di precedenza dei controlli (§4.4) e regole su `unassigned`/`assigneeId` combinati sono scelte tecniche proposte, da confermare.
- Questioni aperte bloccanti: nessuna.

**Punto di approvazione umana:** entrambi i documenti sono stati approvati esplicitamente il 2026-10-19, inclusi l'ordine dei controlli (§4.4) e il `400` per `assigneeId` combinato con `unassigned=true`. Nessun blocco residuo.
